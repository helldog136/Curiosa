# Skins pour Curiosa : décisions du propriétaire (26-27 octobre 2026)

Demande d'origine : « Un Skin définit toute une série de règles d'apparence différentes pour les sites Curiosa. Les skins peuvent radicalement changer l'apparence d'un site tout en ne changeant pas le contenu. Pour une première implémentation, un skin "basic" embarqué avec le cœur ne change rien à l'apparence actuelle de Curiosa : c'est plus une migration. Les skins sont obtenables d'une façon similaire aux modules, via des dépôts git présentant des skins créés par la communauté. Un premier dépôt est curiosa-skins (https://github.com/helldog136/curiosa-skins, cloné dans /home/user/curiosa-skins, vide sauf un README). Crée des skins diamétralement opposés en apparence l'un de l'autre ainsi que du skin de base. » (Demande de l'interroger à fond : « /grill-me ».)

Réponses obtenues :
1. Pouvoir d'un skin : « Je ne sais pas encore » => commencer par VARIABLES (jetons de design) + FEUILLE DE STYLE, sans code exécuté ; concevoir le contrat pour garder la porte ouverte aux gabarits déclaratifs plus tard. Pas de code React fourni par un skin.
2. Réglages d'apparence actuels (palette de 5 couleurs, polices, fond de l'administration) : « Le skin donne les valeurs de départ » : choisir un skin applique ses valeurs ; la personne peut encore les retoucher dans Apparence ; un bouton « revenir au skin » remet les valeurs du skin. Rien n'est perdu pour un site existant.
3. Origine : comme les modules : catalogue officiel (curiosa-skins) relu et installable en un clic, dépôt « personnel » possible avec confirmation explicite, mises à jour depuis l'administration.
4. Le skin « basic » embarqué est LA BASE DE TOUT : il définit un skin pour le cœur ET pour les modules. Si un autre skin ne définit pas une chose utile à l'apparence (cœur ou modules), la valeur de basic s'applique par défaut.
5. Où vivent les parties stylables propres à chaque module : DANS LE MODULE (le module déclare dans son manifeste ses « pièces » stylables et leurs valeurs par défaut, rattachées aux variables communes du skin). Basic ne connaît que le cœur et un vocabulaire commun (carte, bouton, liste, étiquette, etc.) : le cœur reste neutre (leçon de l'audit de généricité : un nouveau module ne doit pas obliger à modifier le cœur ni basic).
6. Repli : valeur par valeur (chaque variable ou règle manquante vient de basic). CONTRÔLE DE LISIBILITÉ AUTOMATIQUE : Curiosa vérifie le contraste (texte/fond, boutons, liens) et refuse ou corrige un skin illisible, avec un message en mots simples.
7. Ressources : polices (woff2) et images EMBARQUÉES dans le dépôt du skin, avec leur licence et des plafonds de taille, servies par le site lui-même ; jamais de Google Fonts ni de CDN tiers chargé chez le visiteur.
8. Skins à créer dans curiosa-skins : LES QUATRE directions : « Brutaliste clair » (fond crème/blanc, grosses bordures noires, ombres dures décalées, monospace, couleurs vives plates, angles droits), « Éditorial papier » (serif élégant, filets fins, grande lisibilité, beaucoup d'espace, tons papier et encre, pas d'ombres, hiérarchie typographique forte), « Rétro néon / arcade » (noir profond, néons magenta/cyan, pixel/mono, lueurs, grilles/scanlines en respectant le mouvement réduit), « Verre / dégradés doux » (surfaces translucides floues, dégradés pastel, très arrondi, ombres diffuses, contraste vérifié). Le basic actuel est sombre, doux, arrondi, sans empattement.
9. Livrable : TOUT, SANS PUBLIER : conception écrite + mécanisme dans le cœur (basic = apparence actuelle à l'identique, VÉRIFIÉE en comparaison d'images sur toutes les pages publiques et tous les modules, clair et sombre ; installation depuis un dépôt, repli, contrôle de lisibilité) + les skins, sur des branches. Le propriétaire verra des captures des skins sur les vraies pages avant toute publication.
10. Administration : NON, site public seulement ; l'administration garde toujours son apparence lisible (un skin illisible ne doit jamais enfermer la personne dehors) ; l'aperçu de l'éditeur montre le skin.
11. Clair / sombre : un skin peut proposer les deux modes ; s'il n'en déclare qu'un, il est imposé ; le visiteur voit le mode de son appareil quand les deux existent.

Principes permanents : « Emma » est un archétype de créatrice non technique, PAS une personne réelle (mots simples, zéro configuration, erreurs sous le champ avec un exemple, mobile d'abord, FR+EN en parité, options avancées repliées) ; neutralité (aucun nom de site réel dans le code/tests/textes par défaut) ; « dézoom » (bornes, pagination, pas de minuteur de fond) ; vie privée (aucun tiers chargé chez le visiteur) ; un propriétaire par donnée ; migration automatique et propre des sites existants (jamais d'action manuelle, jamais de perte).

12. PRINCIPE FONDATEUR (27 octobre 2026) : « Un skin ne définit que de l'apparence, ne faisons pas l'erreur que Grav a faite où les thèmes définissent des éléments de page personnalisés, rendant la migration de thème impossible. » => le contenu et la structure sémantique ne dépendent jamais du skin ; un skin ne peut ni ajouter, retirer, renommer ou masquer un élément porteur de contenu ou d'action ; pas de gabarits déclaratifs ; changer de skin ne fait jamais rien perdre ; un skin qui disparaît se remplace par basic sans perte ; le kit de conformité vérifie ces interdits.

13. PRÉCISION (27 octobre 2026) : « un skin peut clairement changer la mise en page des pages de Curiosa ». => la MISE EN PAGE fait partie de l'apparence et un skin peut la changer radicalement (position/forme de l'en-tête et du menu, colonnes, largeurs, grilles/listes/cartes, ordre visuel des régions, densité, héros, marges). Reste interdit (principe 12) : ajouter, retirer, renommer ou masquer un élément porteur de contenu/d'action, définir blocs/sections/champs/réglages de contenu, injecter du texte. Le cœur doit donc rendre un DOM stable, sémantique et « layout-friendly » (régions nommées `data-skin-region`, pièces `data-skin-part`, grilles pilotables), avec une règle d'accessibilité sur l'écart ordre visuel / ordre de lecture et de tabulation. Pas de JS de skin (le menu mobile reste celui du cœur, stylé par le skin).

14. RÉPONSES AUX QUESTIONS OUVERTES (27 octobre 2026) :
- Vocabulaire : « skin » partout (côté personne aussi) ; la page d'administration garde le titre « Apparence ».
- Retouche des couleurs sur un skin à deux modes : la personne peut passer en mono-mode OU définir ses couleurs pour les DEUX modes, avec avertissement en cas d'illisibilité probable (jamais bloquant pour une retouche).
- Le VISITEUR peut choisir de naviguer en clair ou en sombre (ou automatique) : sans cookie de suivi (stockage local), déclaré dans la confidentialité, script minuscule du cœur sans flash, disponible seulement si le skin fournit les deux modes.
- Crédit « Propulsé par » et lien Confidentialité : constantes non masquables. Lisibilité : AA obligatoire, AAA conseil, basic exempté. Relecture du catalogue officiel : le propriétaire + kit en CI.
- Version : nouvelle majeure (espace réservé 0.4.0 ; à confirmer si 1.0.0). Les modules peuvent aussi passer en majeure quand ils adoptent les pièces de skin et changent leur apparence par défaut.

15. DÉCISIONS TECHNIQUES DU COORDINATEUR (27 octobre 2026), à appliquer par les lots suivants :
- Lot S6 livré (branche feat/skins-s6, bfb1ef1 ; bibliothèque pure src/core/skins/{sanitize,readability,colorParse,allowlist,messages,...}.ts ; postcss devient dépendance directe). API : sanitizeSkinCss, sanitizeTokenValue, checkReadability, correctReadability, probableIllegibility, parseColor.
- Q-B tranchée : la feuille d'un skin PEUT cibler le choix manuel du visiteur : `[data-mode="light"|"dark"]` autorisé en tête de sélecteur (après le préfixe `:root[data-skin="<id>"]`), nécessaire aux skins à deux modes ; à ajouter à l'allowlist avec tests.
- Q-C tranchée : `--sk-color-heading` est un jeton FACULTATIF ; s'il est défini, la paire titres est contrôlée à 3:1 ; sinon la paire est ignorée.
- Le lot « jetons » doit appliquer les mêmes minimums que l'assainisseur aux valeurs de tokens.json (taille de texte ≥ 0,6875rem, etc.), validation par type de chaque jeton.
